# ADR-0007. RBAC: роли поверх прав NPMplus

**Статус:** принято (фаза 3). **Дата:** 2026-10-28.

## Контекст

В NPMplus права пользователя — флаг `admin` в `user.roles` и одна строка `user_permission`: видимость (`user` / `all`) и `hidden` / `view` / `manage` для шести разделов (прокси, редиректы, 404, потоки, списки доступа, сертификаты). Проверки — JSON-схемы в `lib/access/*.json`, которые читает `access.can()`. Пользователи, журнал аудита и настройки доступны только администратору.

NginxionS нужны роли с правами на свои разделы (WAF, PKI, CrowdSec, обучение, сервисы…), встроенные роли (Administrator, Operator, Security Analyst, Viewer), OIDC-группы → роли, и всё это без переписывания upstream-кода (правило «крючков»).

## Решение

- **Таблицы:** `nginxions_role` (имя, описание, `builtin`, `scope` = `all` / `own`, `oidc_groups`), `nginxions_role_permission (role_id, resource, action)`, `nginxions_user_role (user_id, role_id, manual_grant, oidc_grant)`.
- **Модель** (`nginxions/backend/nginxions/rbac/model.js`): ресурсы и действия (`view` / `manage` + особые: `pki:issue`, `pki:revoke`, `pki:export_key`, `waf_policy:apply`, `waf_learning:label`); любое действие включает `view`. Права встроенных ролей задаются в коде и обновляются вместе с NginxionS; в БД у них редактируются только OIDC-группы.
- **Роли — источник прав.** Права нескольких ролей складываются; область «все хосты», если она у любой из ролей.
- **Administrator = флаг `admin` upstream.** Назначение роли ставит или снимает флаг. Изменение ролей, отключение и удаление пользователя оставляют хотя бы одного активного администратора. Проверка и запись выполняются в транзакции под общей блокировкой.
- **Адаптер — два крючка в `lib/access.js`:**
  1. при загрузке пользователя права берутся из ролей (`rbac.resolve`). `user_permission` переписывается как их проекция, если отличается. Upstream-схемы и UI, читающие `user_permission`, работают без изменений;
  2. в `can()` метки ресурсов NginxionS (`waf_policy:manage`…) решает RBAC. Роли открывают разделы, бывшие только для администратора: пользователи (`users:*`), журнал (`audit_log:view`), настройки (`settings:*`). Действия над администраторами остаются за администраторами. Остальное решает схема upstream.
- **Права по пользователям** (`users:permissions`, окно «Права» upstream) заменены ролями: менять их может только администратор, и при следующем запросе пользователя они снова выравниваются по ролям.
- **Эскалация:** нельзя создать, изменить, назначить или снять роль с правами, которых нет у себя. Роль Administrator назначает только администратор.
- **Миграция:** строки `user_permission` неадминистраторов превращаются в роли. Пользователи с одинаковыми правами получают общую роль («NPMplus user» для прав по умолчанию), поэтому права ни у кого не меняются.
- **OIDC:** настраиваемый claim с группами (по умолчанию `groups`), по желанию — scope `groups`. При каждом входе назначения OIDC пересчитываются по группам IdP, в том числе после удаления последней привязки. Ручные назначения действуют независимо. Роль последнего активного администратора сохраняется. Миграция определяет источник прежних назначений из аудита. Старые флаги Administrator и назначения без сведений в аудите сохраняются как ручные. Общий claim настраивает администратор, изменение привязки OIDC требует права делегировать саму роль.
- **Первый администратор:** мастер и настройка из переменных окружения используют общую транзакционную блокировку. Создание пользователя, пароля и проекции прав выполняется атомарно. Пароль не выводится в журнал.
- **Настройки всего развёртывания:** глобальные операции WAF и управление снимками и профилями обучения требуют области «все хосты». Настройки отдельного хоста продолжают проверяться по его области; редактор хоста использует общий каталог объектов WAF без диагностики всего развёртывания.

## Последствия

- Upstream-код не переписан: две метки `NginxionS:` в `access.js`, крючки в `routes/oidc.js`, `HasPermission` (prop `rbac`) и на трёх страницах администрирования.
- Новый пользователь без роли входит, но ничего не видит. После создания пользователя UI сразу предлагает назначить роли.
- Область «конкретные хосты» (ROADMAP, фаза 3: «позже») добавляется отдельной таблицей привязок без изменения этой модели.

## Дополнение: область «свои и выбранные хосты»

Третья область роли — `hosts`: участники видят созданные ими хосты и хосты, перечисленные в роли (`nginxions_role_host`: тип — таблица upstream, id). Роли складываются: роль с областью «все» перекрывает остальные, хосты нескольких ролей объединяются. Фильтр один — `nginxions/rbac/scope.js` (`scopeHosts`); им заменён фильтр `owner_user_id` в `internal/{proxy,redirection,dead}-host.js`, `internal/stream.js`, `internal/report.js` (метки `NginxionS:`) и в модулях NginxionS (хосты, WAF, mTLS). Хосты ролей передаются через `nginxions_hosts` в данных `access.can()`. Проверки `get`, `update` и `delete` применяют область в самом адаптере, включая отдельные запросы WAF, mTLS и истории. Создать или изменить роль с областью `hosts` может только тот, кто сам видит все хосты: иначе можно было бы дать чужие хосты.



## Сервисные API-токены

Администратор выпускает токен в «Администрирование → Роли → Сервисные API-токены». При выпуске он выбирает одну или несколько существующих ролей и срок действия от 1 до 365 дней. Секрет из 32 случайных байтов показывается только при выпуске. В базе хранятся SHA-256 секрета, сроки, ID выпустившего пользователя и связи токена с ролями. Выпуск, изменение ролей и отзыв записываются в аудит в одной транзакции. Когда операция по токену пишет в аудит, метаданные содержат `service_token_id`.

Сервис передаёт `Authorization: Bearer <токен>` по HTTPS. Токен использует права назначенных ему ролей, которые проверяются при каждом запросе. Роль Administrator для токенов недоступна. Область «свои» сама по себе не открывает хосты. Область «свои и выбранные» открывает только перечисленные хосты. Роль с областью «все хосты» открывает глобальные операции в пределах её прав и суммы прав назначенных ролей. Хосты создаются с областью «все хосты». Роль можно заменить без замены секрета. Удаление роли удаляет её назначение. Отзыв или истечение срока блокируют следующий запрос. Удаление или отключение выпустившего аккаунта блокирует его токены. Для плановой ротации выпустите новый токен, переключите сервис и отзовите прежний.

Токены принимают маршруты хостов, списков доступа и сертификатов NPMplus, а также хостовые операции NginxionS, WAF, события, аналитика, обучение, CrowdSec, PKI и mTLS. Глобальные данные событий, статистики, списков доступа, сертификатов, CrowdSec и PKI требуют области «все хосты». Скачивание архива TLS с приватным ключом через upstream-маршрут, загрузка модели агента и управление учётными данными требуют браузерной сессии. API-токен не создаёт сессию и не управляет пользователями, ролями или токенами.

| Запрос с браузерной сессией администратора | Тело и результат |
|---|---|
| `GET /api/nginxions/rbac/service-tokens` | Список и статусы токенов |
| `POST /api/nginxions/rbac/service-tokens` | `name`, `roles` (ID ролей), `expires_in_days`. Возвращает метаданные и одноразовое поле `secret` |
| `PUT /api/nginxions/rbac/service-tokens/{id}` | `roles` (ID ролей). Заменяет назначения |
| `DELETE /api/nginxions/rbac/service-tokens/{id}` | Отзывает токен. Повторный вызов безопасен |

Для маршрутов панели и сервисного API действует общий лимит в 1200 запросов в минуту на адрес клиента. Сервер отвечает `429`, когда лимит исчерпан. Для запросов по токену сервер возвращает `401` при недействительных учётных данных, `403` при отсутствии нужного права и `404`, если запрошенный хост находится вне разрешённой области.
