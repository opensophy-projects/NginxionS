# ADR-0013. Несколько шлюзов в NginxionS и поддержка Traefik в open-appsec

**Статус — предложение.** Статическая проверка исходников завершена. Сборки и испытания новых интеграций входят в приёмку фаз 16–19. Единственный текущий производственный профиль NginxionS остаётся на NGINX/NPMplus.

## Цель

Вернуть исходные интеграции open-appsec, собрать их из проверяемых исходников и дать им функции NginxionS. Traefik должен получить собственное подключение к тому же агенту open-appsec и поддержку из панели NginxionS. Панель ведёт политики, роли, события, PKI и обучение для разных шлюзов. Установка с NPMplus сохраняет действующий формат данных и возможности.

Поддержка фиксируется для конкретной комбинации шлюза, версии, способа развёртывания и функции. Для каждой комбинации нужны отдельные критерии. Например, наличие Docker Compose для Envoy ещё не подтверждает работу Envoy Gateway в Kubernetes, а доступность mTLS не подтверждает проверку отзыва сертификата.

### Очерёдность импорта

1. Зафиксировать точный Git SHA, дерево и требования сборки для каждого компонента. Восстановить каталоги сборки, установщики, манифесты и тесты upstream отдельным изменением на компонент. Обновлённое правило о сохранении исходников оформить в `CLAUDE.md` в том же PR, где возвращаются удалённые каталоги.
2. Дельту NginxionS переносить отдельно по подсистемам. Для агента это локальный режим, генератор политики, rate limits, локальный IPS, метрики, обучение, экспорт признаков и модель. Для attachment это изменения NGINX, проверяемые на исходной интеграции. Для обучения это SmartSync standalone, Shared Files и Tuning. Для каждого набора сравнить сборки и тесты до и после. В рабочей ветке восстанавливать отсутствующие пути и разрешать расхождения явно. Не заменять целиком действующие деревья `openappsec/`, пока перенос локальных изменений не прошёл проверки.
3. Восстановить пути установки, CRD, вебхук и CLI upstream, затем подключить их к локальному профилю. Функции upstream, требующие внешнего сервиса или лицензии, сохранить с их условиями. Проверка профиля NginxionS выполняется без сети и без учётной записи поставщика.
4. Восстановление исходников и включение кода в поставку проверять отдельно. Развёртывания собирают каждый attachment для поддерживаемых версий и архитектур. Устаревшие манифесты служат для совместимости и миграции, пока их контроллеры не проверены на поддерживаемом окружении.

## Общая модель панели

Сохранить сегодняшние операции GUI/API и вынести зависимости от шлюза за адаптер. Адаптер описывает обнаружение и идентичность маршрута, допустимые настройки, подготовку конфигурации, проверку, применение, подтверждение применённой версии и откат. Общие операции берут проверенный набор возможностей из адаптера. Подключённые Kubernetes- и Docker-ресурсы по умолчанию только читаются. При подключении управления фиксируются владелец конфигурации, права на запись и способ избежать конфликтов с GitOps или другим контроллером. У адаптера Docker должны быть права на открытие нужных метаданных, у Kubernetes — доступ только к подключённым ресурсам и namespace. Служба применения не получает общих административных полномочий шлюза.

Идентичность маршрута должна отличать шлюз, узел, provider, namespace, ресурс, правило и порт. Один домен может существовать на нескольких шлюзах. При миграции старые `proxy_host` и `stream` получают соответствия для NGINX с сохранением старых API ID и связей. Остальные правила не привязываются по строковому совпадению домена. Области RBAC, аудит, исключения, обучение и параметры безопасности получают стабильную связь с тем же маршрутом.

Публикуются версионированные снимки конфигурации. GUI показывает отдельно желаемую и подтверждённую версию, ошибки шлюза, ошибки агента и состояние отката. Защищённый маршрут активируется после подтверждения обязательных механизмов. Пакет узла должен содержать совместимую версию контракта, тип шлюза, набор возможностей и идентификаторы маршрутов. Узел отклоняет пакет, который не может применить безопасно.

| Функция | Текущая зависимость | Что переносить |
|---|---|---|
| Действия над маршрутом | `internal/nginx.js`, `templates/`, БД NPMplus | Реестр маршрутов, преобразование в конфигурацию каждого шлюза, валидация и откат. Собственные директивы шлюза хранятся отдельно |
| WAF | `waf/objects/store.js` строит правила по `proxy_host`; `waf/policy.js` записывает локальный YAML и запрашивает применение | Общие объекты и политика, соответствие route → asset, проверка конфигурации, связь события с маршрутом, телеметрия |
| Логи и события | Формат `nginxions_requests` из `nginx.conf`, `events/requests.js` и `events/ingest.js` | Нормализация журналов шлюзов, ID маршрута и узла, сквозной ID запроса, контроль доверенных proxy-заголовков, ротация и дедупликация |
| PKI и mTLS | `pki/mtls.js` генерирует директивы NGINX, CA/CRL и OCSP, значения по путям | PKI и выдача общие. Проверку цепочки, отзыва и ограничений привязки реализовать и испытать для каждого шлюза. Для Traefik `TLSOption` подтверждает поддержку проверки CA. Поведение CRL/OCSP и проверок отдельно для пути проверяется своей приёмкой. [TLS Options](https://doc.traefik.io/traefik/reference/routing-configuration/http/tls/tls-options/) |
| CrowdSec и File Security | `waf/engines.js`, `waf/files.js`, nginx Lua, геофильтрация и страницы отказа | Одна модель политики и событий. На каждом шлюзе проверить применение решений, OpenAPI/anti-bot, проверку файлов ClamAV, GeoIP и ответ при отказе |
| Обучение и пробный прогон | `learning/`, `waf/trial.js`, SmartSync и локальное хранилище | Нормализовать идентификаторы объектов обучения, сопоставлять историю с маршрутами, проверять профили, резервное копирование и обучение между разными узлами |
| Управление и наблюдение | `nginxions-control`, сервисы и пакеты `nodes/package.js` | API узла и проверка состояния по типу шлюза. GUI, CLI и TUI используют те же операции и RBAC. CLI upstream остаётся доступен для операций самого агента |

## Traefik

Первым проверить Go middleware для Traefik с локальным процессом open-appsec attachment. Middleware обрабатывает HTTP-запросы и ответы через `net/http`. Локальный процесс на Go/CGo или C использует API Nano Attachment для жизненного цикла HTTP-сессии и связи с агентом. Так модуль общей памяти и C остаются за пределами интерпретатора Traefik. Связь между процессами локальная, с аутентификацией, ограниченными очередями, сроками и размером сообщений. Начальный вариант — Unix-сокет с ограниченными правами в Compose и локальное подключение в пределах пода в Kubernetes. Публичного инспекционного порта нет. [Traefik Plugins](https://doc.traefik.io/traefik/reference/install-configuration/experimental/plugins/), [ограничения Yaegi](https://github.com/traefik/yaegi#limitations), [API Nano Attachment](https://github.com/openappsec/attachment/blob/2f46293b32c58d5be250aa6d3bac0e4ba9260738/core/include/attachments/nano_attachment.h)

Сначала доказать, что локальный плагин в выбранной версии Traefik получает необходимые события и загружается без сети. Если он не обеспечивает нужную работу с ответами, потоками или таймаутами, сравнить собственный build Traefik с компилируемым middleware и вариант выделенного HTTP-фильтра в тракте. Сравнение должно учитывать управление отказами, стоимость сопровождения и отсутствие скрытых изменений трафика. Документированный `ForwardAuth` вызывает внешнюю службу авторизации до передачи запроса. Его проверку можно использовать как ограниченный эксперимент для входящего запроса. Полная приёмка требует событий и вердиктов также для ответа приложения. [Traefik ForwardAuth](https://doc.traefik.io/traefik/reference/routing-configuration/http/middlewares/forwardauth/)

Контракт первой реализации включает запрос и ответ целиком по фазам обработки: начало сессии, метаданные, заголовки, тело порциями, окончания и очистку. Middleware обязано сохранить семантику запроса, backpressure, отмену, лимиты и порядок middleware. Тесты отдельно фиксируют, когда вердикт успевает остановить запрос до upstream или ответ до первой записи клиенту. Для уже начавшегося ответа документируется действие и оно проверяется. WebSocket Upgrade и длительные gRPC/SSE-соединения требуют отдельных гарантий для рукопожатия, сообщений и потока. Трафик без завершения TLS на доступном шлюзе, raw TCP/UDP и фаза 14 L3–L7 имеют отдельный контракт. GUI не показывает для них HTTP-инспекцию без фактической проверки.

## Приёмка и порядок работ

1. **Фаза 16 — исходники и сборка.** Цель — восстановить пять upstream-деревьев, собрать upstream-профили и перенести изменения NginxionS проверяемыми наборами. Закрытие требует сохранения текущего стека, сборок исходных интеграций, тестов ABI, лицензий и обновления с действующей версии. Первый коммит фиксирует происхождение исходников. Первый вариант Traefik можно исследовать параллельно на восстановленном Nano Attachment. Первый результат фазы состоит из сверки дерева, восстановления исходников attachment и отдельной сборки текущего NGINX и одного upstream-профиля с тем же агентом.
2. **Фаза 17 — панель и исходные шлюзы.** Выделить адаптер, поддержать смешанный набор шлюзов, миграцию ID и связей. Закрытие требует проверить общие функции и отличия каждого профиля из таблицы, локальный запуск, доверенные сетевые границы, RBAC и работу каждой операции из GUI.
3. **Фаза 18 — Traefik.** Провести проверку пригодности транспорта и закрепить способ интеграции. Затем пройти ту же матрицу функций, включая Compose, File и Docker, Kubernetes Ingress, IngressRoute и Gateway API. Профили Kubernetes проходят независимую проверку прав, обнаружения и обновления. Релиз включает сборки, тесты и примеры конфигураций с точными версиями. Интеграцию с агентом можно использовать независимо от панели.
4. **Фаза 19 — совместная приёмка.** Проверить миграцию с NPMplus и управление смешанной инсталляцией. Закрытие требует офлайн-установки, обновления, отката, отказа агента и шлюза, отсутствия потери событий, целостного обучения и документации по каждой подтверждённой комбинации.

Минимальная матрица CI для каждого заявленного профиля включает:

- загрузку attachment, apply/rollback политики, корректные запросы и ответы, режимы Detect/Prevent, подтверждение блокировки штатной тестовой фикстурой;
- отсутствие подтверждения защиты при недоступном агенте, таймаутах, переполнении очереди или неподдерживаемом маршруте, нагрузку в пределах тестового лимита и восстановление после перезапуска;
- TLS/mTLS, отзыв, изоляцию RBAC, проверку источника IP, события, журналы, корреляцию, ClamAV/CrowdSec, профили обучения и обновление модели;
- HTTPS с HTTP/1.1, HTTP/2 и HTTP/3 там, где профиль обещает поддержку. Отдельные проверки multipart, сжатия, больших тел, WebSocket, gRPC, SSE и вывода телеметрии согласно контракту профиля;
- совместимость подписанных пакетов между версиями, смешанные узлы, приватные локальные каналы, офлайн-установку, SBOM, SAST и проверку образов.

Частичная реализация отмечается как экспериментальная. Профиль считается готовым, когда опубликованная матрица подтверждает каждую обещанную функцию, включая семантику отказа и ограничения протоколов. Неподдерживаемое сочетание отклоняется при проверке конфигурации с конкретным объяснением.
