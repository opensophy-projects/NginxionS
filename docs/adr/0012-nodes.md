# ADR-0012. Несколько серверов: управляющий сервер и узлы

**Статус:** принято (фаза 15). **Дата:** 2026-11-20.

## Контекст

NginxionS ставят на несколько серверов (решение 20.11.2026, `docs/ROADMAP.md`, фаза 15). Нужно управлять ими из одной
панели, учить агентов вместе и ставить новые серверы сразу обученными. Облако производителя агента (my.openappsec.io, Fog) не
используется: всё работает в закрытом контуре.

Что уже есть:
- `node_id` в таблицах событий, журнала запросов, обучения, PKI и CrowdSec (строка, `local` по умолчанию; ADR-10 плана).
  Код разбора событий принимает узел параметром (`classify(raw, nodeId)` и др.).
- PKI NginxionS (ADR-0009): свои CA, выпуск по CSR, отзыв, CRL.
- Агент ходит к локальным сервисам без токена Fog (ADR-0011), поэтому общее обучение через `smartsync` возможно без облака.

## Решение

1. **Роли.** Управляющий сервер (manager) — обычный NginxionS с GUI и Postgres. Узел — тот же образ: nginx, агент,
   CrowdSec. Отдельной настройки роли нет: сервер, подключённый к manager, — узел; сервер, к которому подключены
   узлы, — manager; без того и другого — самостоятельный сервер. `node_id` строк, пришедших с узла, — его
   идентификатор (`n-<16 hex>`), строк самого manager — по-прежнему `local`.
2. **Узел ходит к manager (pull), а не наоборот.** Узлу не нужны входящие порты: он может стоять за NAT. Manager
   принимает узлы на своём API (порт панели).
3. **Регистрация одноразовым кодом.** Администратор добавляет узел в «Агенты → Узлы» и получает код
   `<id узла>.<секрет>` (24 часа, хранится только хэш). На новом сервере в GUI «Подключить к управляющему серверу»
   вводятся адрес manager и код. Узел сам создаёт ключ (он не покидает узел) и CSR с CN = id узла; manager проверяет
   код и подписывает CSR доменом доверия «NginxionS Nodes» своей PKI (создаётся сам при первой регистрации).
   Код после этого недействителен.
4. **Доверие к manager.** При подключении узел запоминает отпечаток сертификата панели manager (доверие при первом
   подключении) и дальше принимает только его. Администратор сверяет отпечаток: он показан на обоих серверах.
5. **Канал до шага 15.2.** Heartbeat и запросы узла идут на API manager с токеном узла (выдаётся при регистрации,
   хранится только хэш). Отдельный порт с mTLS на сертификате узла — шаг 15.2 (раздача конфигурации): тогда токен
   заменяется сертификатом, а отзыв сертификата (CRL) отключает узел и на уровне TLS.
5a. **Пакет конфигурации (шаг 15.2).** Хосты, отданные узлу в «Агенты → Узлы → Хосты», уходят на него пакетом:
   прокси-хосты, их сертификаты (свои и PKI; сертификаты ACME остаются на manager — их продлевает он), списки
   доступа, режимы WAF. Пакет подписан ключом Ed25519 manager (создаётся сам в томе данных); открытый ключ узел
   получает при регистрации и закрепляет. Версия — SHA-256 канонической формы содержимого: heartbeat сообщает её
   узлу, узел забирает пакет только когда она изменилась. На узле строки пакета становятся своими строками с меткой
   «управляемые» (`nginxions_managed`: id на manager → id на узле); свои хосты узла не трогаются, хост с доменом,
   который уже обслуживает узел, пропускается и попадает в отчёт. Если nginx отверг хост, узел возвращает прошлый
   пакет и сообщает ошибку; эту версию он больше не пробует (когда manager отменил изменение и снова предлагает
   применённый пакет, узел снимает ошибку).
   Хосты узла — свои и хосты его меток («Агенты → Узлы → План выкатки → Хосты по меткам», таблица
   `nginxions_label_host`). Manager хранит последние 20 пакетов, выданных каждому узлу (`nginxions_node_package`), и
   может удержать узел на одном из них: «Пакеты → Вернуть этот пакет» — откат на одном узле (`pinned_by = manual`).
   Поэтапная выкатка (настройка `cluster.rollout`): при включении узлы, кроме канареек, удерживаются на пакете,
   который у них работает (`pinned_by = staged`), изменение получают только канарейки; «Выкатить на все узлы»
   переводит удержанные узлы на текущую конфигурацию; выключение снимает удержание выкатки. Удержанный пакет
   выдаётся как есть, той же подписью и версией.
   **Канал узла — mTLS.** После регистрации узел обращается к manager с SNI `nginxions-cluster`: на порту панели это
   отдельный сервер nginx (`npmplus.conf`), который просит сертификат клиента (`ssl_verify_client optional_no_ca`) и
   передаёт его backend заголовком `X-NginxionS-Node-Cert` (`conf.d/nginxions-cluster.conf`; на любом другом имени
   заголовок пуст, клиент не может его подставить). Backend принимает запрос узла только с его токеном и тем
   сертификатом, который PKI выдала этому узлу (отпечаток), в сроке и не отозванным. Браузеры это имя не запрашивают,
   поэтому панель никогда не просит у них сертификат. Регистрация по одноразовому коду идёт без сертификата.
   В пакете также страница блокировки и настройки CrowdSec manager (профили, allowlist, сценарии, bouncer) — без
   секрета капчи, он у каждого сервера свой. Узел применяет их теми же функциями, что GUI, и только когда они
   отличаются от его настроек; ошибка (например, капча без секрета на узле) показывается у узла, хосты пакета при
   этом остаются применёнными.
5b. **События узлов (шаг 15.3).** После каждого heartbeat узел отправляет manager свои новые события безопасности
   (по 500, не больше 5000 за раз, курсор — последний отправленный id; история до подключения не отправляется).
   Manager берёт только известные колонки, ставит `node_id` узла из его токена и сохраняет их обычным хранилищем
   событий: их видят «События», аналитика и уведомления, а фильтр «Узел» показывает события одного сервера.
   Manager недоступен — курсор стоит на месте, ничего не теряется. Так же уходит журнал запросов узла (по 1000, не
   больше 20 000 за heartbeat, свой курсор): manager хранит строки с id узла и считает почасовые агрегаты, поэтому
   «Аналитика» и «События → Все» видят трафик всех серверов; фильтр «Сервер» в аналитике и журнале запросов, разбивка
   «Серверы».
   **Общие баны.** Свои баны сервера — активные решения его CrowdSec (сценарии, баны агента и ручные), кроме
   блок-листов, центрального API и банов кластера. Узел отправляет manager их список, когда он меняется; manager
   хранит списки узлов (`nginxions_cluster_ban`) и сам держит их баны. Баны кластера для сервера — свои баны manager
   и всех остальных узлов (самый долгий бан адреса); heartbeat сообщает их версию, узел забирает список и держит его в
   своём CrowdSec решениями с origin `nginxions-cluster`: недостающие добавляются, ушедшие из списка снимаются, так
   что разбан на сервере, где был бан, доходит до всех (`crowdsec/cluster-bans.js`).
5c. **Общее обучение (шаг 15.4).** smartsync собирается в образ агента и работает на manager в режиме standalone:
   REST `/api/sync`, блокировка файлом, без Kafka, Redis и tenant облака. Tenant агента без облака — `local`, его
   файлы лежат в корне shared storage (`/<asset>/…`); smartsync NginxionS читает и пишет там же. Роль сервера
   NginxionS определяет сам и пишет в настройки агента (`nginxions-agent.env`), перезапуская агент при изменении:
   - сервер с активными узлами — manager: smartsync включён, `LEARNING_HOST` агента — smartsync этого сервера;
   - узел — его агент учится через manager: `SHARED_STORAGE_HOST` и `LEARNING_HOST` — ретранслятор NginxionS на
     127.0.0.1 узла (7817, 7818), который передаёт запросы на API manager по закреплённому TLS с токеном узла;
   - самостоятельный сервер учится локально, как раньше.
   Manager пропускает от узла чтение любых файлов обучения (общее состояние, разметка) и запись только данных окна
   (`…/window_<d>_<n>/<агент>/data.data`), подставляя в путь id узла: данные каждого узла лежат под его id, и узел
   не пишет за другой. smartsync знает узел по этому пути: когда в окне есть данные двух узлов и больше, источники
   одного узла засчитываются не больше чем `MinSources − 1`, так что один узел (или тот, кто его захватил) не
   делает значение нормой в одиночку; источник, размеченный в GUI как доверенный, считается как раньше. Общее состояние (`remote/`), состояние агента (`processed/`) и разметку узел не пишет —
   это делают smartsync и GUI manager. Разметка GUI manager (`tuning/decisions.data`) действует на всех узлах.
   Снимок обучения на manager с узлами хранит и общее состояние, сведённое smartsync (файлы `remote/` хранилища), а
   откат снимка возвращает его вместе с состоянием агента manager; автоматический снимок там — каждый час (48 штук),
   так что сводку smartsync, давшую резкий сдвиг нормы (уведомление `learning_shift`), можно откатить на час назад.
   Пороги smartsync (сколько разных источников и окон обучения нужно значению, какая доля источников) задаются в GUI
   («Агенты → Узлы → Обучение узлов»): NginxionS пишет их в `nginxions-smartsync.json` рядом с настройками агента,
   smartsync читает файл перед каждой сводкой (метка `NginxionS:` в его коде).
   Проверяется тестом стека `cluster` (`scripts/test-cluster.sh`): обычный трафик с трёх источников через три сервера
   становится нормой, запросы тех же трёх источников только через один узел — нет. Окна обучения там — минута:
   тестовая переменная `NGINXIONS_LEARNING_INTERVAL_MINUTES` (WAF агента берёт её как `learning.intervalDuration`
   вместо параметра политики, smartsync — как интервал сводки; метки `NginxionS:`), в работе её нет.
   Manager недоступен — узел защищает с тем, чему уже научился; данные окна, которые не дошли, пропадают (агент
   шлёт следующие).
5d. **Профили обучения (шаг 15.5).** Профиль — выученное агентом по выбранным сайтам (файлы их asset, формат снимка
   обучения), с тем, где и когда он снят, подписанное ключом Ed25519 сервера (тем же, что пакеты узлов). Профиль
   применяется на этом сервере (выученное по его сайтам заменяется, остальные сайты не трогаются, сначала снимок
   текущего состояния), скачивается и загружается на другом NginxionS — подпись проверяется ключом внутри файла,
   а GUI показывает отпечаток ключа и отличает свои профили от загруженных. Один профиль manager отмечается «для
   новых узлов»: его id и версия входят в пакет каждого узла с хостами, узел забирает файл один раз по версии
   (`GET /api/nginxions/nodes/learning/profile` по закреплённому TLS с токеном), проверяет, что подписан ключом
   manager, который узел закрепил, и заполняет только те сайты, по которым сам ещё ничего не выучил: своё
   обучение узла профиль не перезаписывает. Дальше узел учится вместе со всеми (5c). Ошибка (manager занят, агент
   не ответил) показывается у узла, повтор — не чаще раза в 10 минут.
   Профиль может нести и политику WAF своих сайтов («С политикой WAF сайтов»): режимы сайтов и их location и
   ссылки на объекты политики — по виду и имени (id на разных серверах разные), вместе с самими объектами
   администратора (встроенные есть на каждом сервере). При применении «и политику WAF» сайт ищется по доменам, объект
   с тем же видом и именем используется как есть (не перезаписывается), недостающий создаётся; что не нашлось,
   показывается (`learning/profile-policy.js`).
5e. **Модель агента на узлах (шаг 15.5).** Продвинутая модель, загруженная на manager («WAF → Агент»), раздаётся
   узлам: её SHA-256 и размер входят в подписанный пакет, узел скачивает файл (`GET /api/nginxions/nodes/model`,
   закреплённый TLS, токен узла) потоком в файл рядом с моделью, сверяет хэш с пакетом, ставит на место (прежняя
   модель сохраняется) и перезапускает агент. На manager нет модели — узел возвращается к модели образа. Откат —
   «Вернуть прежнюю модель» на manager: модели меняются местами, узлы следуют со следующим пакетом. На узле модель
   загружать нельзя: её задаёт manager. Ошибка скачивания показывается у узла, повтор — не чаще раза в 10 минут.
5f. **Команды узлу (шаг 15.6).** Manager к узлу не обращается, поэтому команда («перезапустить агент») ждёт в
   строке узла и уходит ему в ответе на следующий heartbeat; узел выполняет её один раз по id и сообщает в следующем
   heartbeat, что сделал (или ошибку), — это видно в «Выкатке». Новая команда заменяет ждущую. Команды:
   `restart_agent` (перезапуск агента), `collect_logs` (узел присылает по закреплённому каналу последние строки
   логов каждого сервиса своего стека, секреты скрыты узлом; manager хранит последние логи каждого узла). Каждый
   heartbeat узла несёт и состояние контейнеров его стека: «open-appsec» и «CrowdSec» на manager показывают его
   для выбранного узла.
6. **Отключение узла.** «Отключить» отзывает сертификат узла, удаляет хэш токена и помечает узел отключённым:
   следующий heartbeat получает 403, узел показывает это у себя и продолжает работать самостоятельно.
7. **Local-first.** Узел без связи с manager защищает сайты как раньше; недоступный manager не мешает запуску узла.
   Все запросы к manager — с таймаутом.
8. **Права.** Новый ресурс RBAC `nodes`: `view` (список узлов), `manage` (добавить, новый код, отключить, удалить).
   Подключить свой сервер к manager — `settings:manage`. Обучение кластера (пороги smartsync, профиль для новых
   узлов, откат снимка с общим состоянием) — `waf_learning:sync`.

## Последствия

- Одна база — на manager. Отказ manager не останавливает защиту на узлах; резервный manager (HA) — вне фазы 15:
  сначала резервная копия и восстановление.
- Совместимость версий: узел сообщает свою версию; пакет конфигурации (15.2) несёт версию схемы, узел старше или
  младше manager на одну версию работает.
- Доверие при первом подключении уязвимо к подмене в момент подключения; отпечаток в GUI на обоих серверах позволяет
  это заметить, а mTLS шага 15.2 закрывает канал после регистрации.
