# ADR-0012. Несколько серверов: управляющий сервер и узлы

**Статус:** принято (фаза 15). **Дата:** 2026-11-20.

## Контекст

NginxionS ставят на несколько серверов (решение 20.11.2026, `docs/ROADMAP.md`, фаза 15). Нужно управлять ими из одной
панели, учить агентов вместе и ставить новые серверы сразу обученными. Облако Check P (my.openappsec.io, Fog) не
используется: всё работает в закрытом контуре.

Что уже есть:
- `node_id` в таблицах событий, журнала запросов, обучения, PKI и CrowdSec (строка, `local` по умолчанию; ADR-10 плана).
  Код разбора событий принимает узел параметром (`classify(raw, nodeId)` и др.).
- PKI NginxionS (ADR-0009): свои CA, выпуск по CSR, отзыв, CRL.
- Агент ходит к локальным сервисам без токена Fog (ADR-0011), поэтому общее обучение через `smartsync` возможно без облака.

## Решение

1. **Роли.** Управляющий сервер (manager) — обычный NginxionS с GUI и Postgres. Узел — тот же образ: nginx, агент,
   CrowdSec. Отдельной настройки роли нет: сервер, подключённый к manager, — узел; сервер, к которому подключены
   узлы, — manager; без того и другого — самостоятельный сервер. `node_id` строк, пришедших с узла, — его
   идентификатор (`n-<16 hex>`), строк самого manager — по-прежнему `local`.
2. **Узел ходит к manager (pull), а не наоборот.** Узлу не нужны входящие порты: он может стоять за NAT. Manager
   принимает узлы на своём API (порт панели).
3. **Регистрация одноразовым кодом.** Администратор добавляет узел в «Агенты → Узлы» и получает код
   `<id узла>.<секрет>` (24 часа, хранится только хэш). На новом сервере в GUI «Подключить к управляющему серверу»
   вводятся адрес manager и код. Узел сам создаёт ключ (он не покидает узел) и CSR с CN = id узла; manager проверяет
   код и подписывает CSR доменом доверия «NginxionS Nodes» своей PKI (создаётся сам при первой регистрации).
   Код после этого недействителен.
4. **Доверие к manager.** При подключении узел запоминает отпечаток сертификата панели manager (доверие при первом
   подключении) и дальше принимает только его. Администратор сверяет отпечаток: он показан на обоих серверах.
5. **Канал до шага 15.2.** Heartbeat и запросы узла идут на API manager с токеном узла (выдаётся при регистрации,
   хранится только хэш). Отдельный порт с mTLS на сертификате узла — шаг 15.2 (раздача конфигурации): тогда токен
   заменяется сертификатом, а отзыв сертификата (CRL) отключает узел и на уровне TLS.
5a. **Пакет конфигурации (шаг 15.2).** Хосты, отданные узлу в «Агенты → Узлы → Хосты», уходят на него пакетом:
   прокси-хосты, их сертификаты (свои и PKI; сертификаты ACME остаются на manager — их продлевает он), списки
   доступа, режимы WAF. Пакет подписан ключом Ed25519 manager (создаётся сам в томе данных); открытый ключ узел
   получает при регистрации и закрепляет. Версия — SHA-256 канонической формы содержимого: heartbeat сообщает её
   узлу, узел забирает пакет только когда она изменилась. На узле строки пакета становятся своими строками с меткой
   «управляемые» (`nginxions_managed`: id на manager → id на узле); свои хосты узла не трогаются, хост с доменом,
   который уже обслуживает узел, пропускается и попадает в отчёт. Если nginx отверг хост, узел возвращает прошлый
   пакет и сообщает ошибку; эту версию он больше не пробует.
5b. **События узлов (шаг 15.3).** После каждого heartbeat узел отправляет manager свои новые события безопасности
   (по 500, не больше 5000 за раз, курсор — последний отправленный id; история до подключения не отправляется).
   Manager берёт только известные колонки, ставит `node_id` узла из его токена и сохраняет их обычным хранилищем
   событий: их видят «События», аналитика и уведомления, а фильтр «Узел» показывает события одного сервера.
   Manager недоступен — курсор стоит на месте, ничего не теряется. Журнал запросов узла остаётся на узле.
5c. **Общее обучение (шаг 15.4).** smartsync собирается в образ агента и работает на manager в режиме standalone:
   REST `/api/sync`, блокировка файлом, без Kafka, Redis и tenant облака. Tenant агента без облака — `local`, его
   файлы лежат в корне shared storage (`/<asset>/…`); smartsync NginxionS читает и пишет там же. Роль сервера
   NginxionS определяет сам и пишет в настройки агента (`nginxions-agent.env`), перезапуская агент при изменении:
   - сервер с активными узлами — manager: smartsync включён, `LEARNING_HOST` агента — smartsync этого сервера;
   - узел — его агент учится через manager: `SHARED_STORAGE_HOST` и `LEARNING_HOST` — ретранслятор NginxionS на
     127.0.0.1 узла (7817, 7818), который передаёт запросы на API manager по закреплённому TLS с токеном узла;
   - самостоятельный сервер учится локально, как раньше.
   Manager пропускает от узла чтение любых файлов обучения (общее состояние, разметка) и запись только данных окна
   (`…/window_<d>_<n>/<агент>/data.data`), подставляя в путь id узла: данные каждого узла лежат под его id, и узел
   не пишет за другой. Общее состояние (`remote/`), состояние агента (`processed/`) и разметку узел не пишет —
   это делают smartsync и GUI manager. Разметка GUI manager (`tuning/decisions.data`) действует на всех узлах.
   Manager недоступен — узел защищает с тем, чему уже научился; данные окна, которые не дошли, пропадают (агент
   шлёт следующие).
6. **Отключение узла.** «Отключить» отзывает сертификат узла, удаляет хэш токена и помечает узел отключённым:
   следующий heartbeat получает 403, узел показывает это у себя и продолжает работать самостоятельно.
7. **Local-first.** Узел без связи с manager защищает сайты как раньше; недоступный manager не мешает запуску узла.
   Все запросы к manager — с таймаутом.
8. **Права.** Новый ресурс RBAC `nodes`: `view` (список узлов), `manage` (добавить, новый код, отключить, удалить).
   Подключить свой сервер к manager — `settings:manage`.

## Последствия

- Одна база — на manager. Отказ manager не останавливает защиту на узлах; резервный manager (HA) — вне фазы 15:
  сначала резервная копия и восстановление.
- Совместимость версий: узел сообщает свою версию; пакет конфигурации (15.2) несёт версию схемы, узел старше или
  младше manager на одну версию работает.
- Доверие при первом подключении уязвимо к подмене в момент подключения; отпечаток в GUI на обоих серверах позволяет
  это заметить, а mTLS шага 15.2 закрывает канал после регистрации.
